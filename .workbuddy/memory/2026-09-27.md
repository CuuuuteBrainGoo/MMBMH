## v1.2.0 — 少爷提的 7 条 + 一个真 bug（2026-09-27 凌晨）

### 少爷提的 7 条

1. **API Key 掩码显示**：保留头尾各 3 字符，中间固定 3 个星号
2. **版本号管理**：迭代很多版还停在 1.1.0，是我的机制问题
3. **`bets` 是什么意思**：核对页冲突直接渲染内部路径，用户看不懂
4. **非彩票能不能上传前拦掉**（附加约束：超过 1 秒就别做）
5. **3 张 4 月双色球永远卡在「等待开奖结果」**（真 bug）
6. **首页一键兑奖**
7. **过期票状态**：未中奖就是未中奖；中奖未兑用绿色显示并计入过期账

### ★ 第 5 条的真根因（本轮最重的修复）

`DrawResultClient.PAGE = 50`。双色球每周 3 期 → 50 期 ≈ **3.8 个月**。
少爷 4 月的票距今 5 个月，接口返回里**根本没有那一期** →
`fetch()` 返回 null → 被判成「官方还没公布」→ `markAwaiting` →
状态永远 `AWAITING_RESULT` → `needingCheck` 的 SQL 每晚又把它捞出来 → **死循环**。

**改了三处**：
1. `PAGE` 50 → **200**（约 15 个月）
2. 新增 `DrawResultClient.Lookup` 三态（`Found` / `NotInList` / `RequestFailed`）——
   以前「查不到」和「请求失败」都压成 null，调用方无法区分，只能一律当"还没公布"
3. 新增 `TicketStatus.RESULT_UNAVAILABLE`（查不到开奖结果）：
   - 开奖日过去 ≤ `STALE_DAYS`(3 天) → 仍当"还没公布"，继续等
   - 超过 3 天 → 判定查不到，转人工，**不再进自动重试队列**
   - 详情页给两个手动出口：「我核对过了，没中奖」/ 填金额记为中奖

**顺带修了文案骗人**：`checkAllPending` 的汇总把 `AwaitingResult` 和
`ResultUnavailable` 都算进「都没中」——少爷就是因为看到「核验了 3 张，都没中」
但列表还挂着「等待开奖结果」才发现不对。抽成 `PrizeService.summarize()` 纯函数（可单测）。

**性能顺带修**：批量核验 N 张票 = N 次全量拉取（每次几百 KB）。
加 `allOf()` 缓存（TTL 10 分钟）+ `checkAllPending` 开头 `clearCache()`。

### 第 4 条：本地预筛（`core/ImageGuard.kt` + `ImageStats`）

**诚实边界**：上传前 100% 判断做不到（本地没有视觉模型）。做到的是：
- **硬拦**：全黑（亮度 < 25）、整片同色（亮度标准差 < 6）→ 直接失败，**不发请求**
- **只记日志不拦**：色彩鲜艳（饱和度 > 0.42）—— 票放彩色桌布上拍是正常用法，拦了是误伤
- **模型侧兜底**：解析层报「彩种未识别」时，`BatchTriage.looksLikeNotTicket()` 判定，
  批量里归「跳过」而不是「失败」，单张时给专门的文案

**性能（少爷约束：超过 1 秒就别做）**：
第一版写的是 `small.getPixel(x, y)` 逐点取 —— **4096 次 JNI 调用**。
改成 `getPixels(IntArray)` 一次取整块 + 把计算抽到 `ImageStats.fromArgb()`（纯数组遍历）。
`ImageStatsTest` 里有**耗时上限断言**（100ms，实测微秒级）钉住这个优化。

### 第 1 条：掩码的陷阱

掩码本身很简单，**真正的坑是「掩码被当成真 Key 存进去」** ——
用户只改模型名就点保存的话，密钥会静默变成 `ark***e9b`，下次识别 401 且看不出原因。
双保险：UI 层判一次 + `saveProvider`/`testProvider` 里再判一次（`ApiKeyMask.isUnchangedMask`）。
另外星号**固定 3 个**，不随长度变 —— 连密钥长度都不泄露。

### 第 3 条：`bets` → 人话

根因是 UI 直接渲染内部路径。新增 `core/ConflictText.kt` 做翻译：
- `bets` → 「注数 / 投注内容」（它有两种来源：注数不一致 / 没读到投注内容）
- 下标从 **1** 数起（内部是 0 基，弄反了用户会核对错那一注）
- `main`/`second` 按彩种说成「红球/蓝球」或「前区/后区」
- **两种前缀都要认**：`bets[0]`（TicketDiffer 产出）和 `bet[0]`（BetRules 产出）

同时 `TicketDiffer` 的差异值通过 `Outcome.conflictValues` / `PendingEntry.conflictValues`
带到 UI，显示「主识别：5 注　复核：3 注」。

### 第 6 条：一键兑奖

`PrizeService.redeemAll()` —— **只处理 `TO_REDEEM`**。
不碰 `PRIZE_PENDING`（§15 要求金额人工确认）、不碰 `EXPIRED_UNCLAIMED`（钱已经没了）。
UI 二次确认框写清「会兑几张、合计多少钱」。

### 第 2 条：版本号机制（★ 踩了个连锁坑）

**机制**：`version.properties`（唯一来源）→ gradle 读它 → `_pack.py` 打包前比对 + 警告。

**踩的坑**：改完之后 `pack_ledger.py` 里的
`re.search(r'versionName\s*=\s*"([^"]+)"', build.gradle.kts)` **抓不到了**（因为源码里不再硬编码），
`or "0.0.0"` 兜底 → 打出来的是 **`LotteryLedger-v0.0.0-*.apk`**，
而且脚本**一路 rc=0**，看起来完全正常。

**教训**：**把配置收成单一来源时，必须全项目搜一遍谁在读旧位置**。
只改定义方、漏改读取方 = 静默产生错误产物。
顺手也把 `_dexprobe2.py` 里写死的 APK 路径改成 glob 取最新。

### 第 7 条：过期票配色

新增 `LedgerColors.Expired = Color(0xFF4E8C3A)`（绿，少爷指定），
刻意跟 `Spend` 的墨绿错开 —— 两个状态语义相反（钱到手了 / 钱白扔了）。

**顺带干掉一处重复**：首页 `StatusChip` 和详情页 `StatusChipLarge` 各有一份

## v1.3.0 — 拜拜财神（受保护清空）+ 日志按周清空（2026-09-27 凌晨）

### 功能一：「拜拜财神」受保护的一键清空

**入口**：设置页「版本」卡片下方一行 —— 左边 App 图标，右边「拜拜财神，从头来过。」
刻意长得像**普通信息行**（无按钮样式），危险操作不该让人"看着就想点"。

**两道门**：
1. **连点 13 次**（少爷指定，模仿安卓开发者模式）
   - 前 6 次**什么都不提示**（真·隐藏入口）
   - 第 7 次起提示「还差 N 次」
   - **1.5 秒连续窗口**：间隔超时就从 1 重数 —— 落实「一次性连续点击」这个要求，
     否则今天点 6 次 + 明天点 7 次也能凑够
2. **连续 3 次确认**，文案逐次递进：
   - ① 「真要跟财神说再见？」+ 提示可以先导出备份
   - ② 「第二次确认」+ **列出具体数字**（N 张票 / M 注 / 购彩合计）
   - ③ 「最后一次了」+ 说明设置会保留，确认按钮用警示红

**清空范围**（少爷要求：不得改动任何设置项）：
| 清 | 不清 |
|---|---|
| tickets / ticket_bets / drafts / draw_results / edit_logs / recognition_runs | **ai_providers**（平台配置）、**app_settings**（思考强度等）、Keystore 里的 API Key |

**不用 `db.clearAllTables()`** —— 那个会清掉全部 8 张表。改成逐表 DELETE，
包在 `db.withTransaction { }` 里（票和注是两张表，删到一半失败会留下"有注没票"的残局）。

**清空后**：日志记 `[Wipe] 用户清空了台账：票 N / 注 M / …`，
临时图片兜底清一遍，界面状态整体复位。

**新增纯逻辑**：`core/TapSequence.kt`（连点计数，可单测）。

### 功能二：日志按周清空

`core/LogRetention.kt`（纯函数）+ `LogFileSink.sweepWeekly()`，在 `LedgerApp.onCreate` 里
**同步执行、且在写启动日志之前**（顺序反了会让刚写的「启动」那条立刻被清）。

**基准文件** `files/logs/.last_sweep`：
- 放在日志目录而不是 `app_settings` 表 —— 那张表是**用户设置**，会被备份/恢复覆盖，
  日志轮转属于程序内部维护记录，混在一起两边都不干净
- 清空时**不删它**（删了下次又算"首次运行"，永远清不掉）

**三个"不清"的边界**（都会静默出错，必须写测试）：
1. 首次运行（无记录）→ **只建立基准**，不清。否则装好当天就清掉刚写的启动日志，且每次启动都清
2. 未满 7 天 → 不清
3. **时钟回拨**（now < last）→ 保守不清。宁可多留几天，也别因为时间乱跳删日志

**判据是「距上次清空 ≥ 7 天」不是「日志最老那条有多老」**：
日志行只有 `时:分:秒` 没有日期，按天裁不现实 → 整份清掉（也正是"每周清空一次"的字面意思）。

### ★ 踩的坑

1. **Room 的 `@Query` 是编译期注解（RetentionPolicy.CLASS），运行时反射读不到。**
   第一版守护测试想用注解反射把 SQL 全捞出来，结果一条都拿不到 →
   `assertTrue("一个 wipe 方法都没找到")` 失败。
   **改成读源文件做静态检查**，反而更强：还能抓到 `clearAllTables` 这种**没有 SQL 字符串**
   的危险写法（注解反射根本看不见它）。
2. `@Query.value` 在 Kotlin 里是**单个 String**（不是 `String[]`）—— 第一版按数组写，编译报错。
3. SettingsScreen 用 `R.drawable.*` 忘了 `import com.bro.lotteryledger.R`。

### 守护测试（`WipeScopeGuardTest`，5 个用例）

静态检查 `Daos.kt` / `LedgerRepository.kt`：
- 所有 `DELETE FROM <表>` 的表名必须在白名单（6 张业务表）
- 6 张业务表**每张都有**清空语句（防漏清留孤儿数据）
- `AiProviderDao` / `AppSettingDao` 段落里**不能出现 DELETE**
- 仓储层**不能出现** `clearAllTables`
- 白名单本身不能含疑似设置表的表名

> 读源码的测试依赖 workingDir：Gradle unit test 的 cwd 是模块目录（`app/`），
> 所以试了 `src/...`、`app/src/...`、`../app/src/...` 三个位置，**都找不到就断言失败**
> （静默跳过等于白写）。

- 版本 **1.3.0 / versionCode 4**（加功能升 minor，符合立下的规则）
- `_dexprobe2.py` 锚点扩到 150+，MUST_BE_ABSENT 加 3 个新测试类

## v1.3.0（第二批）— 过期票口径 + 注数交叉验证 + 公益贡献（2026-09-27 凌晨）

### ① 过期未兑奖：加负号 + 排除出「中奖」

**改的是统计 SQL**（`TicketDao.stats`）：
`prizeConfirmed` 加条件 `AND ticket_status != 'EXPIRED_UNCLAIMED'`。

原因：过期票转状态时 `prize_amount` 是**保留**的（要显示"作废了多少钱"），
不过滤的话那笔永远拿不到的钱会被算进「中奖」→ 净收支凭空多一笔收入。

口径（少爷原话：「总购彩支出等账目里按未中奖算，忽略过期未兑奖金金额」）：
- `purchase` 照算（钱确实花出去了）
- `prizeConfirmed` **不含**过期票
- `expired` 单独统计，界面绿色 + **负号**

### ② 两种过期票，统一落点

| 类型 | 处理 |
|---|---|
| A. 录入时没过期、之后过期 | `sweepExpired` 扫 `TO_REDEEM`（原本就有） |
| B. **录入时就已经过期** | 核验时**当场**标过期，不经过 `TO_REDEEM` |

新增私有 `PrizeService.landAfterWin(t, amount)` —— 三条路（自动核验 / 确认金额 /
手动记中奖）都走它，避免各写一份。

分错的后果很实在：「待兑奖」的语义是"还能去兑"，一张废票挂在里面，
用户会白跑网点，而且「待兑」金额看着像能拿到的钱。

`Outcome.Won` 加 `expiredUnclaimed` 字段，核验提示改成
「中了 N 注（¥X），但录进来时兑奖期就已经过了 —— 这笔钱作废了」。

### ③ 注数交叉验证（`core/TicketCrossCheck.kt`）

少爷反馈「大部分需要确认的都是 `bets`」，并给出思路：
「用票面信息做交叉验证…只有出现演算异常时才应该确认」。

他的判断是对的。实现：
```
有效注数 = 票面金额 ÷ (单注价 × 倍数)
单注价从 LotterySpecs 读（不硬编码，避免和规则引擎不一致）
```
`TicketDiffer` 里注数不一致时先仲裁：
- **主识别与金额吻合** → 抑制冲突（`canSuppressConflict`），只记日志
- 复核吻合但主识别不吻合 → **仍要打扰**（主识别错了，而界面上是主识别的结果）
- 都对不上 → 打扰

冲突文案也升级成「5 注（与票面金额吻合）」。

### ④ 公益贡献（`core/PublicWelfare.kt`）

**财政部 2026 年第 24 号公告**：双色球与超级大乐透的公益金提取比例**都是 36%**
（奖金 51% + 发行费 13% + 公益金 36%）。2 元一注 → 0.72 元；3 元追加票 → 1.08 元。
少爷举的 20 元 → 7.2 元完全吻合。

公益金 = 票面金额 × 36%，首页 hero 卡下方单独一条（金色，不混进净收支）。

**为什么用推算而不是读票面**：读票面值要加数据库字段，
而 Room 配的是 `fallbackToDestructiveMigration()` —— **加字段会清空真实账目**。
为一个小数冒这个风险不值。界面写明「按 36% 估算」。

### ★ 本轮踩的坑

1. **`pack_ledger.py` 的新鲜度检查把 `src/test` 也算进去了** →
   改一个测试文件就判定「debug APK 比源码旧」→ 文件名加 `-STALE` → 返回 2 →
   `_pack.py` 判定失败**跳过了整个签名步骤**（用户拿不到签名包）。
   修：只扫 `src/main`（那才进 APK）+ `version.properties`；`rc=2` 不再阻断后续步骤。
2. **`Room` 的 `@Query` 是 `RetentionPolicy.CLASS`**（编译期注解），运行时反射读不到 →
   守护测试改成读源码做静态检查（详见技能 `silent-dead-feature-audit` 形态七）。
3. **守护测试判据过宽**：把 `DELETE FROM ai_providers WHERE id=:id`（删单个平台，正当功能）
   当成违规；注释里的 `clearAllTables` 字样也被自己抓成违规。
   修：只禁「没有 WHERE 的整表清空」+ 检查前先剥注释。
4. **dex 里搜短版本号字符串是假阳性**：`1.2.0` 一直报"仍存在"，
   查下去是 **Kotlin 标准库的文档注释**（`Added since 1.2.0 for binary compatibility...`）。
   → 版本号改为读 APK manifest（`aapt2 dump badging`）比对 `version.properties`。
5. `@Query.value` 在 Kotlin 里是**单个 String**（不是数组），按数组写会编译错。
6. SettingsScreen 用 `R.drawable.*` 忘了 `import com.bro.lotteryledger.R`。

## v1.3.1 — 单式多注误报 + 提示条居中配色（2026-09-27 上午）

少爷报两条（附核对页截图）：

### ① 「标为单式但存在多注（5 注）」是误报

- **根因**：`BetRules.validate` 判 `!declaredMultiple && totalUnits > 1`。
  但**单式本来就可以多注** —— 5 注单式的 totalUnits 就是 5，于是每张多注单式票都被报警。
- **正确判据**：看**单注**号码个数有没有超过单式所需。
  新增 `Bets.hasMultiBet(type, bets)` / `Bets.firstMultiBetDetail(type, bets)`，
  `inferType` 与校验共用同一个判据（单一真相）。
- 提示语改具体：「标为单式，但 **第 N 注 红球选了 8 个**（单式只需 6 个），像是复式」
  —— 用户得知道哪一注哪个号码组有问题。
- ⚠️ **潜在坑**：为消掉提示而手改成「复式」，会让注数从 5 变成组合数展开，账目直接错。
  验收清单 29.1 里专门写了这条警告。

### ② 提示框遮挡底部按钮 + 分不清好坏消息

- 原来用 `SnackbarHost`（贴底），盖住「继续核验」「录入彩票」；中奖/未中奖/过期一个灰黑块。
- 新增 `core/Notice.kt`（`NoticeKind` + `Notice`），`_toast` 类型 `String?` → `Notice?`。

### ★ 最重的教训：GitHub 密钥扫描是「模式匹配」，不是「值有效性判断」

被拦了**两次**：

| 轮次 | 文件里的内容 | 结果 |
|---|---|---|
| 第 1 次 | 一个**真实的**火山方舟 Key（形如 `ark-` + 8-4-4-4-12-5 分段） | 拦（合理） |
| 第 2 次 | 换成占位符，但**保持了真 Key 的形状**<br>（`ark-` 前缀 + 全 0 的 8-4-4-4-12 分段 + 5 位后缀） | **又被拦！** |

> ⚠️ 本文档**故意不记录真实 Key 原文** —— 2026-09-27 第二次推送时，
> 正是因为这里原文抄了真 Key，`.workbuddy/memory/2026-09-27.md:931`
> 被 GitHub Push Protection 拦下（commit `a38046a`）。
> **记录踩坑时也不要抄真实凭据**，描述形状/前缀就够说明问题。

**我第 2 次的思路错在哪**：以为「换成假值」就安全了，特意保留
`ark-` 前缀 + 8-4-4-4-12-5 分段"让测试长度用例能过"。
但扫描器**看到形状就报**，根本不管值能不能用。

**正确做法**：测试数据用**完全不像密钥**的中性字符串
（现在用 `abcdefghijklmnopqrstuvwxyz`）。测试关心的是
「头尾各留 3 个字符」这条规则，用什么字符串毫无影响 ——
为了"像真的"而保留形状，是**零收益的纯风险**。

**顺带**：`ark-` 这个前缀我第一轮自查时**漏掉了**，
因为我只列了 `sk-` / `Bearer` / `bce-v3` 这些常见前缀。
→ **扫密钥不能只列前缀，要让每条命中都人工过一眼。**

### 沙箱网络：GitHub 有时通、有时不通

- `git ls-remote` / `git push` 从沙箱跑 → `CONNECT tunnel failed, response 502`
- `git clone --depth 1` → **成功**（后续验证用的就是它）

所以别把 502 当"永久不通"下结论，但**交付动作（push）不要押在沙箱网络上**。

### GitHub 连接器：能读不能写

`mcp__github__get_me` / `list_branches` / `get_file_contents` 都正常，
但 `push_files` 报：

```
403 Resource not accessible by integration
PUT .../contents/README.md
```

`integration` = 连接器本身。查 `/settings/installations` 可见它的权限里
**只有 `gists` 的写权限，没有 `Contents: Read and write`**，
且页面底部明确写着「has not been installed on any accounts」。
→ **OAuth 授权 ≠ GitHub App 安装**；要写仓库必须安装 App。

**我犯的流程错误**：没先用一个最小写操作试水，就规划了 10 批、
生成完所有 JSON 才撞墙。**下次先验证最关键的假设再做计划。**

### `.bat` 脚本编码（第二教训）

第一版脚本用了「UTF-8 BOM + `chcp 65001` + 中文提示」，
结果 cmd 把中文全解析成乱码方块，**把真正的报错淹没了**。

根因：`chcp 65001` 是**脚本开始执行后**才切编码，
而 cmd 读脚本内容是在此**之前**，此时中文已按 GBK 解错。

**现在的做法**（`推送到GitHub.bat`，已验证可用）：
- 脚本本体 **100% ASCII**，零中文
- 中文说明另放 `PUSH-README.txt`（UTF-8 BOM，记事本正常）
- 换行**全 CRLF**、无 BOM、无裸 LF

静态检查项：非 ASCII 字节数 = 0、`%` 成对、goto 标签配套、括号配对。

### 其他

- 重建 git 历史（`rm -rf .git`）会**连 remote 一起删掉**，必须重新
  `git remote add origin`。用户第一次跑 bat 就撞在这一点上
  （`fatal: 'origin' does not appear to be a git repository`）。
- `.gitignore` 里用「排除所有 APK、只 `!` 放行当前版本」的写法，
  升版时只改一处；旧 APK 永久排除（二进制进 git 历史删不掉）。
- 推助手的两个文件（`推送到GitHub.bat` / `PUSH-README.txt`）
  已加进 `.gitignore` —— 路径写死本机，别人 clone 也用不上。
