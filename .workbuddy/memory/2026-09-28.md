### 九、推送 —— 历史重写导致必须强制推送

**关键发现：不能直接 `git push`。**

```
远端 origin/main 真实值  = ef4562c  （含旧 APK 的那版，已被重写掉）
本地重写后 HEAD         = dff8ccc
```

`ef4562c` 在本地已完全不存在（`git cat-file -t ef4562c` → Not a valid object name），
历史彻底分叉 → 普通 push 被拒：`! [rejected] main -> main (fetch first)`。

**解决方案（顺带升级了 bat）**：

改造 `推送到GitHub.bat` 为**两段式推送**：
1. 先试普通 `git push`（正常情况就够了）
2. 被拒（捕获 `non-fast-forward` / `fetch first` / `rejected`）→ 提示用户
   **手动输入 YES** 确认 → 走 `git push --force-with-lease`

用 `--force-with-lease` 而不是 `--force`：远端被别人动过时会自动中止，不会静默覆盖。

> 踩坑：第一版把检测写成「被拒后再跑一次 `git push`」，**等于推两次**。
> 改成把首次 push 输出存进 `%TEMP%\mmbmh_push_*.log`，`findstr` 读一次即可。

**bat 校验（按 `windows-script-encoding` 技能）**：
- 字节级：`非ASCII=0  CRLF=191  裸LF=0  首3=40 65 63` ✅
- cmd 实跑：模拟 non-fast-forward → 降级提示触发 → force-push 分支走到 → `[SUCCESS]` ✅
- 无错误关键字，stderr 干净

### 十一、本次新增的通用经验

1. **剔历史要写精确路径** —— `git rm -r --cached <目录>` 会连目录下的文档一起剔，
   且工作区文件同步消失。别拿目录当粒度。
2. **重写历史后 tag 会悬空** —— 必须逐个重指到新历史的对应提交，再 `push --force` tag。
3. **force push 后服务端不立即瘦身** —— 客户端干净 ≠ 服务端干净，别把「仓库 size 没降」
   当成瘦身失败。
4. **推送前先 `git ls-remote` 拿远端真实值** —— 本地 `origin/main` 可能是陈旧缓存，
   我差点据此误判「可以 fast-forward，不用强推」。
5. **bat 改造要测「降级分支」** —— 正常路径谁都测得到，被拒后的分支才是真需求所在。

## 修复：开奖时刻判定只比日期（少爷 18:14 报）

### 现象

大乐透 **26111 期**，票面开奖日 **2026-09-28**（就是当天），**当晚 21:30 才开奖**。
下午 **18:12** 打开 App，首页就弹「有 1 张彩票已过开奖日期」。
列表里那张票的 chip 也显示「等待开奖结果」，顶部「待开奖」计数 = 1。

### 根因：同一个判断，两套实现，漂移了

| 位置 | 代码 | 判断 |
|---|---|---|
| 核验层 `PrizeService.isDrawTimePassed` | `now.hour >= 22` | ✅ **对的**：当天 22:00 后才算过点 |
| 查询层 `Daos.needingCheck` | `WHERE draw_date <= :today` | ❌ **只比日期**，不管几点 |

→ 09-28 一到，票就被捞进待核验队列 → 黄条 + 计数 + 详情页按钮全部误判。

### 修法：收敛到唯一口径

新建 `core/DrawSchedule.kt`（纯函数、零依赖）：

- `drawTimePassed(drawDate, today, now)` —— 当天 22:00 之后才算过点
- `checkCutoff(today, now)` —— **22:00 前返回「昨天」**，过了 22:00 才返回今天
- `effectiveStatus(stored, drawDate, today, now)` —— 展示层修正存量票

**`checkCutoff` 是最妙的一处**：不去 SQL 里拼时间，而是把「截止日」提前一天 ——
`draw_date <= cutoff` 就**天然等价于** `drawTimePassed == true`，
跨月/跨年由 `LocalDate.minusDays(1)` 自动处理，不用写任何特判。

改动 8 个文件：

| 文件 | 改了什么 |
|---|---|
| `core/DrawSchedule.kt` | **新增** —— 唯一口径 |
| `repo/PrizeService.kt` | `isDrawTimePassed` 委托给 DrawSchedule（API 不变，旧测试不动） |
| `repo/LedgerRepository.kt` | `initialStatus` + `needsCheck` 改用新口径 |
| `db/Daos.kt` | 参数名 `today` → `cutoff`（注释写清「它**不是**今天」） |
| `ui/HomeScreen.kt` | chip 走 `effectiveStatus`；文案「已过开奖**日期**」→「**时间**」 |
| `ui/TicketDetailScreen.kt` | chip 走 `effectiveStatus`；当天开奖显示「今天开奖，还没到开奖时间」 |
| `LedgerApp.kt` | 启动补核验日志文案 |
| `test/.../DrawScheduleTest.kt` | **新增 22 条测试** |

### 为什么 UI 层也要改（存量票）

`initialStatus` 只在**入账时**跑一次，写完库就不再变 ——
少爷那张票库里已经是 `AWAITING_RESULT`，光改查询改不掉它。
所以展示层用 `effectiveStatus` 动态修正：`AWAITING_RESULT` + 还没到点 → 显示「未开奖」。
**纯计算、不写库**，其它状态（已中奖/已兑奖/查不到……）一律不动。

### 验证

- 全量 **481 用例 / 0 失败 / 0 错误**（新增 22 条），编译 BUILD SUCCESSFUL
- 其中一条**遍历 24 小时**验证 `checkCutoff` 与 `drawTimePassed` 口径等价 ——
  以后谁只改其中一个，这条测试就会红

### 通用教训 ★

**同一个业务判断有多个消费者时，必须收敛到唯一来源。**

这次是「核验层知道要等 22:00，查询层只认得日期」——
两套逻辑**各自看都对**，合起来就错。而且错得隐蔽：不开奖日的票全都正常，
只有「开奖日当天、22:00 之前」这个时间窗才暴露。

凡是「这个判断会被 UI / 查询 / 核验分别用到」，就该：
1. 抽成**纯函数**（可注入 now，能单测）
2. 加一条**「各消费者等价」的测试**钉住（光测单个函数挡不住漂移）
