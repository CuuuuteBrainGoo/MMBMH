### 九、推送 —— 历史重写导致必须强制推送

**关键发现：不能直接 `git push`。**

```
远端 origin/main 真实值  = ef4562c  （含旧 APK 的那版，已被重写掉）
本地重写后 HEAD         = dff8ccc
```

`ef4562c` 在本地已完全不存在（`git cat-file -t ef4562c` → Not a valid object name），
历史彻底分叉 → 普通 push 被拒：`! [rejected] main -> main (fetch first)`。

**解决方案（顺带升级了 bat）**：

改造 `推送到GitHub.bat` 为**两段式推送**：
1. 先试普通 `git push`（正常情况就够了）
2. 被拒（捕获 `non-fast-forward` / `fetch first` / `rejected`）→ 提示用户
   **手动输入 YES** 确认 → 走 `git push --force-with-lease`

用 `--force-with-lease` 而不是 `--force`：远端被别人动过时会自动中止，不会静默覆盖。

> 踩坑：第一版把检测写成「被拒后再跑一次 `git push`」，**等于推两次**。
> 改成把首次 push 输出存进 `%TEMP%\mmbmh_push_*.log`，`findstr` 读一次即可。

**bat 校验（按 `windows-script-encoding` 技能）**：
- 字节级：`非ASCII=0  CRLF=191  裸LF=0  首3=40 65 63` ✅
- cmd 实跑：模拟 non-fast-forward → 降级提示触发 → force-push 分支走到 → `[SUCCESS]` ✅
- 无错误关键字，stderr 干净

### 十一、本次新增的通用经验

1. **剔历史要写精确路径** —— `git rm -r --cached <目录>` 会连目录下的文档一起剔，
   且工作区文件同步消失。别拿目录当粒度。
2. **重写历史后 tag 会悬空** —— 必须逐个重指到新历史的对应提交，再 `push --force` tag。
3. **force push 后服务端不立即瘦身** —— 客户端干净 ≠ 服务端干净，别把「仓库 size 没降」
   当成瘦身失败。
4. **推送前先 `git ls-remote` 拿远端真实值** —— 本地 `origin/main` 可能是陈旧缓存，
   我差点据此误判「可以 fast-forward，不用强推」。
5. **bat 改造要测「降级分支」** —— 正常路径谁都测得到，被拒后的分支才是真需求所在。
