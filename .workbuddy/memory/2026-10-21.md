## 三、验证：重构必须证明「没有行为漂移」

这是本轮最关键的一步 —— 改了 10 个脚本的路径来源，光「能跑」不够。

| 验证 | 结果 |
|---|---|
| `py_compile tools/*.py`（warning 当错误） | 全过 |
| `python tools/doctor.py` | 全绿，密钥指纹匹配，`HEAD=a25c8f3` |
| `python tools/_pack.py`（端到端） | BUILD-DEBUG / BUILD-RELEASE / PACK / SIGN **全 rc=0**，3 分 11 秒 |
| **APK md5 与改造前对比** | **完全相同** —— debug `cda94de7…`，release `9cb053c8…` |
| `_release_guard.py` | PASS（4 处一致） |
| `_secret_sentinel.py` | CLEAN（18 commits + 160 files） |

**md5 一致 = 同一份源码产出了逐字节相同的包** → 重构零漂移。
这比"跑通了"强得多，也是以后验证工具链改动的标准手段。

## 四、踩到的坑：仓库里的 `http.proxy` 变成了陷阱

`git push` 报：

```
fatal: unable to access '...': Failed to connect to github.com:443
over proxy 127.0.0.1 after 2060 ms
```

仓库级 config 里躺着 `http.proxy = http://127.0.0.1:10090`（之前少爷跑 bat 时写入的），
但那个代理现在没开 → **所有 git 操作都失败**，而且 `git ls-remote` 直接**空输出**
（不报错、就是没结果），特别容易误判成"远端没这个分支"。

**处置**：`git -c http.proxy= push` 直连 → 成功。确认直连稳定后
`git config --unset-all http.proxy` 清掉这个陷阱。

**教训**：代理配置会「过期但继续生效」。下次再见到 `over proxy 127.0.0.1`
先试直连，别急着让少爷开代理。
