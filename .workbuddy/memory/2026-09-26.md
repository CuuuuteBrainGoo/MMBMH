### 不可违背的产品原则（交接稿 §23，已写进代码）
1. AI 只读票 —— 模型禁止判中奖/算奖金/按规则猜号码（提示词里三条硬禁令）
2. 照片不长期保存 —— 私有 cacheDir + 重新编码 JPEG（天然剥 EXIF）+ 确认后即删 + 启动清理
3. 同一实体票不重复入账 —— 靠**票身份指纹**（三优先级）
4. **号码全同也是两张票** —— 投注内容指纹**仅提示**，`FingerprintsTest` 专门锁死这条
5. 票面开奖日期优先
6. 一二等奖只判奖级，奖金手填；待确认时不给最终盈亏（首页显式提示）
7. 弱指纹（彩种+期号+时间+金额）**只能提示不能阻断**

### 编译期踩到的真实缺陷（已全部修复）
1. `OpenAiCompatibleClient`：在 `use{}` 的 inline lambda 里用 `continue` → Kotlin 报
   "break continue in inline lambdas is experimental"。改成 `while` 循环 + `return@use`。
2. `RecognitionOrchestrator`：`diff.isEmpty` 少写括号（Map 要调方法）。
3. `LedgerRepository`：`BetType` 没有 companion，`BetType.from()` 不存在
   → 改成包级私有函数 `betTypeFrom()`。
4. `MainViewModel`：`Prepared.bytes` 是 `Int`（字节数），却当成 `ByteArray` 传给指纹函数
   → 给 `Prepared` 加 `sha256Bytes()` 从临时文件读回。
5. `ReviewScreen`/`SettingsScreen`：`androidx.compose.foundation.layout.FlowRow` 全限定名写法
   **不被 Kotlin 接受**，必须 import + `@OptIn(ExperimentalLayoutApi::class)`。
6. `RawTicket.purchaseTime` / `amountYuan` **缺默认值**，导致测试里命名参数构造失败。
   按 §2.3「看不清就返回 null」的本意，两者补 `= null`。

## v1.1.0 — 真机 404 事故 + 版本号/日志页/返回逻辑（17:00-17:40）

### ★★★ 最严重的一次事故：改了代码但没进编译

**现象**：改了 4 个源文件 + 新增 1 个测试类，跑 `testDebugUnitTest` 报
「BUILD SUCCESSFUL / 1 executed, 38 up-to-date」，测出 43 个用例全绿。
**但那些全是旧代码的结果。新代码一行都没编译。**

**根因**：**存在两个独立的工程目录，不是一个！**

| 目录 | 角色 | 说明 |
|---|---|---|
| `F:\Projects\MMBMH-mony mony back my home\LotteryLedger` | **权威源码**（少爷工作区） | 中文路径，是我平时 Read/Edit 的地方 |
| `F:\LottBuild\LotteryLedger` | **编译副本** | ASCII 路径，当初为了避开 Gradle/aapt2 中文路径问题拷出来的 |

两者**不是符号链接**（realpath 各自独立）。我在工作区改，编译目录还是旧版，
所以「编译通过」是假象。

**确诊手法（可复用）**：对两边同名文件算 md5 + 比 mtime。
```python
hashlib.md5(open(path_a,'rb').read()).hexdigest()
os.path.getmtime(path_b)
```
本次实测：4 个文件 md5 全 DIFFER，编译目录时间戳停在 16:27-16:28（改动前），
新测试类在编译目录里直接不存在。

**永久修复**：重写 `F:\LottBuild\run_build.py`，**每次跑 Gradle 前先做正向同步**
（工作区 → 编译目录，按「大小+内容」判是否需拷贝，跳过 build/.gradle），
并反向清理编译目录里已被删除的源文件。现在会打印 `sync: N copied, M removed`。

### 另一个坑：run_build.py 的参数解析 bug
原脚本 `OUT = sys.argv[1]`，导致 `run_build.py testDebugUnitTest` 时
**把任务名当成了输出文件名**，实际执行 `gradle`（无任务）→ 秒过 → 假成功。
还在 `F:\LottBuild` 下生成了一个名叫 `testDebugUnitTest` 的垃圾文件。
新版要求 `run_build.py <输出文件> <任务...>`，参数不足直接打 usage 退出。

### 少爷真机报的 bug：HTTP 404（token=0）
- 「AI 调用 4 次，累计 token 0」→ 请求根本没到推理层
- 实测豆包端点：`/api/v3`、`/api/v3/chat/completions`、带尾斜杠
  **全部返回 401**（认证层先拦，任何路径都不会 404）
- 结论：404 来自**用户填了基础地址**（火山控制台显示的就是 `…/api/v3`）
- **修复**：新增 `core/EndpointNormalizer.normalize()`，用 `java.net.URL` 解析
  （不用字符串尾部匹配），补 `/chat/completions`、剥尾斜杠、丢 query/fragment。
  接在三处：保存时落库前、请求前兜底、设置页实时预览「实际请求：…」
- 同时修掉「404 响应体为空 → 报错只有『HTTP 404：』」的问题，
  新增 `describeFailure()` 按状态码给人话 + 下一步（401→Key 无效，404→地址不对…）

### 少爷要求的三件事（v1.1.0）

   显示在首页标题下 + 设置页底部。versionName 1.1.0 / versionCode 2。
2. **日志页**：`core/LedgerLog.kt`（内存环形缓冲 500 条，纯 Kotlin 可单测）
   + `core/LogFileSink.kt`（落盘 `filesDir/logs/ledger.log`，256KB 轮转）。
   装 `Thread.setDefaultUncaughtExceptionHandler` 抓崩溃 + sleep 250ms 保证落盘。
   UI `ui/LogScreen.kt`：级别色条、全部/警告+/仅错误筛选、**系统分享导出**（主用途）。
3. **返回逻辑**：`MainActivity` 用 `BackHandler` 统一处理 ——
   核对页 → 弹「放弃这张票？」二次确认；子页 → 回首页；
   首页 → 「再按一次返回退出」（2 秒窗口）。核对页顶栏 ✕ 也走同一个 `onBack`。

## 追加 4 — 真机日志揭示真相：识别要 124 秒，超时再次修正 ★

**少爷的真机日志（两张票都识别成功并入了账，任务实际是成功的）**：

1. **模型真的要跑 45 秒～2 分钟，不是卡死。** 用户看到「一直在识别」纯粹是因为

4. **待确认的矛盾**：旧代码 `callTimeout = timeoutSeconds + 10`，
   若 timeoutSeconds 为默认 45，则 callTimeout 只有 55 秒，
   但 124 秒的请求却成功了。两种可能：
   (a) 少爷手动改过超时（>114 秒）；(b) OkHttp 的 callTimeout 在服务端分块响应时未按预期生效。
   **需要向少爷确认「设置 → 编辑平台 → 超时(秒)」显示多少。**

## 追加 6 — 修 bug + 思考强度三档开关

**少爷反馈 4 条**：①准确性没变差 ②🐛冷启动后点「录入彩票」跳设置页 ③深度思考做成开关

### ② 的根因（值得记住的教训）

`MainViewModel.init { refreshAll() }` **只加载了账本数据，没加载平台列表**。
`_providers` 初始是 `emptyList()`，首页「有没有可用平台」的判断永远读到空 →
误判成「还没配平台」→ 跳设置页。进过一次设置页就好了（设置页会触发 `loadProviders()`），
所以只在「冷启动后直接点录入」时复现 —— 也就是每次都复现。

**修复**：`init` 里补 `loadProviders()`。

**教训**：App 启动时只加载了「一部分」必要状态。以后凡是新增依赖启动状态的判断，
都要回头检查 `init` 是否覆盖到 —— 这类 bug 不报错，只在特定操作路径上暴露。

### ⚠️ 核心教训：做完状态流转，必须检查每个状态的「出度」

这次差点漏掉的不是代码 bug，而是**流程断头路**：
状态机里 `PRIZE_PENDING → TO_REDEEM → REDEEMED` 这条链，
`TicketStatus` 枚举里状态定义齐全、判奖逻辑也正确，
但**中间两个状态没有任何 UI 能触发流转** —— 等于死状态。

自检清单（以后做任何状态流转都要过一遍）：
1. 列出所有状态
2. 对每个状态问：**谁能让它变成下一个状态？**（代码里的调用方在哪？）
3. 出度为 0 的状态：要么是终点（NOT_WON / REDEEMED / EXPIRED 合理），
   要么就是漏了入口（本次中招的就是这种）
4. 出度靠 UI 触发的，还要检查**按钮在界面上真的存在且可见**

### 关键设计决定（都有理由，别改）

| 决定 | 理由 |
|---|---|
| **JSON，不拷 SQLite 文件** | ① DB 开 WAL，只拷 `.db` 会**静默丢最后一批写入**（用户以为备份成功）② 跨版本恢复会撞 `fallbackToDestructiveMigration` → 反而清空数据 |

| **API Key 不进备份** | §17 硬要求 |
| **不备 recognition_runs / drafts** | 运行日志性质，非账目 |
| **`toString(2)` 缩进格式** | 大 30%，换**人可读** —— App 起不来时能用文本编辑器抄号码 |
| **`id` 保留在文件里但导入时归零** | 文件里保留便于人肉比对；入库时让 Room 重分配（否则撞主键） |
| **OpenDocument 的 mime 用 `*/*`** | 有些文件管理器把 `.json` 报成 octet-stream，限死 application/json 会让备份文件在选择器里**变灰选不中** |

### 坑与对策

1. **org.json 的 `optString()` 遇到 `JSONObject.NULL` 返回字符串 `"null"`**
   → 取值前必须 `isNull(k)` 判断。已在 codec 里收成 `str()/lng()/dbl()` 等 helper。
   **专门写了测试**：可空字段往返后必须还是 null，不是 `"null"` 字符串。
2. **`import` 是 Kotlin 软关键字**，用作函数名合法但易读性差 → 改叫 `restore`。
3. **反射测字段集**不能用 `kotlin.reflect.memberProperties`（要引 kotlin-reflect）
   → 改用 `::class.java.declaredFields`。
   **踩了两次**：
   - ① 只按 `isSynthetic` 过滤**不够** —— Compose 编译器会给每个 data class 生成
     `public static final int $stable`，它是 **static 而非 synthetic**，过滤不掉。
   - ② 正确过滤条件是 **两个都要**：
     `filter { !Modifier.isStatic(it.modifiers) }` + `filter { !it.name.startsWith('$') }`
   - 这条测试当场就红了，报 `was:<[$stable, appVersion, ...]>` —— 这正是它存在的意义：
     它检查的是「字段集是不是我以为的那样」，而不是「某个字段在不在」。
   - 顺带注意 Kotlin 里 `"$"` 这种单字符 `$` 字符串容易让解析器犯迷糊，写 `'$'`（Char）最稳。

### ⚠️⚠️ 硬伤一：`FieldRow` 的 `onEdit` 从来没被调用

```kotlin
// 组件定义（旧）
private fun FieldRow(label: String, value: String, onEdit: () -> Unit) { ... }  // onEdit 没用到
// 调用处（旧）
FieldRow("期号", ticket.issue ?: "—") {
    onChange { it.copy(issue = it.issue) }    // ← 看着像在改，其实是空操作
}
```

**后果：AI 把期号或开奖日期读错，用户没有任何办法修正，只能放弃重拍。**

```
入账     → 删草稿（出队）
放弃     → 删草稿（出队）
闪退/退出 → 草稿还在，首页提示可点进去接着核对
```
好处：不引新表、不引 WorkManager，复用 §16 已有的草稿机制。

**③ 分诊的优先级（判错的代价是双向的）**

```
1. EXACT_DUPLICATE      → 跳过（最高优先，重复的票哪怕结构完美也不该入账）
2. POSSIBLE_DUPLICATE   → 人工
3. !validation.ok 或 conflicts 非空 → 人工
4. 其余                 → 可直接入账
```
`validation.ok` 的语义是「**连警告都没有**」——**有 WARNING 也算要人工**。
比如「票面金额与推算对不上」是个真问题，自动入账等于把错误固化进账目。

**④ 「自动入账」只处理最近一批**

`lastBatchDraftIds` 是成员变量，只装这一批的草稿 id。
不去碰历史遗留草稿 —— 否则少爷可能没看清就把旧的也入账了。
循环里实时同步（`lastBatchDraftIds = newDraftIds.toList()`），
这样**中途取消时已识别的票也能用「直接入账」**。

### 顺手修的老 bug：草稿只进不出

以前 `commitPending` 成功后**不删草稿**，导致：
- 首页「有 N 笔识别草稿还没确认入账」永远不消失
- 草稿越攒越多

现在：`PendingEntry` 带 `draftId`，入账/放弃时删对应草稿。
`discardPending` 也删 —— 草稿存在的意义是「防闪退丢票」，不是当回收站。
