## 一、技能库：新增「形态十三」

**改的文件**：`~/.workbuddy/skills/silent-dead-feature-audit/SKILL.md`（572 → 691 行）

### 为什么值得单独加一条，而不是并进已有的形态六

技能里原本有「形态六：同一段 `when`/映射被复制到多处」。看着像，其实**不是一回事**：

| | 形态六 | 本轮（新形态十三） |
|---|---|---|
| 代码长什么样 | **一模一样**，被复制粘贴 | **完全不一样** —— 一个是 Kotlin `if`，一个是 SQL `WHERE`，一个是建票分支 |
| 怎么发现 | diff / 肉眼对比就能看出来 | **diff 和 review 都看不出来**，因为它们"长得不像" |
| 何时暴露 | 改了一处漏一处，立刻可见 | **只在特定时间窗**（开奖日当天 22:00 前那几小时） |

**新形态：同一个业务判断被多处独立实现 → 口径漂移**

- **判据**：问「这个业务规则，代码里有几个地方在回答它？」
- **排查**：搜**判据的形状**（`hour >= 22` / `draw_date <=`），不搜变量名
- **危险信号**：同一个名词（`today` / `now`）在不同函数里含义不同 —— 本项目 DAO 参数名叫 `today` 实际值是"昨天"，就是漂移前兆
- **修法两步（缺一不可）**：
  1. 抽**纯函数**，时间必须**可注入**（`LocalDate.now()` 参数化，否则测不了边界）
  2. 加**「各消费者等价」的对拍测试** —— 遍历 24 小时断言 `checkCutoff` 与 `drawTimePassed` 给出同一答案

**第 2 步是关键**：只测单个函数挡不住未来的漂移。以后谁把边界从 `>= 22` 改成 `> 22`，这条测试立刻红。

**顺带改的**：
- frontmatter `description`：十二类 → **十三类**，补上新形态 + 新触发场景
  （「明明还没到点 / 明明符合条件，它却说到了 / 不符合」）
- 第 12 节末尾的**交付前自查清单**加一条对应检查项

**验证**：章节编号 `grep '^## \d+\.'` → **0~14 连续无缺号**（原来 12 之后直接跳 14，缺 13）。

## 二、哨兵：修掉一个「假 CLEAN」漏洞

**改的文件**：`F:/LottBuild/_secret_sentinel.py`（三处副本已同步，md5 一致）

### 怎么发现的

按流程跑提交前哨兵时，我在脚本目录 `F:\LottBuild` 裸跑了一次 —— 输出是：

```
[1/2] scanning git history ...
      !! NOT A GIT REPO - history scan SKIPPED
[2/2] scanning working tree ...
      mode: plain directory walk (not a git repo)
==============================================================
  RESULT: CLEAN - safe to push
==============================================================
```

**历史扫描被跳过了，却照样打印 `RESULT: CLEAN`。** 脚本装在 `F:\LottBuild`，那里根本不是 git 仓库 —— 真正要扫的仓库在 `F:\Projects\...`。这一跑等于白跑，但屏幕上给的是绿灯。

这和我摔过四次的那类坑**是同一个病**：**站在"我看着没问题"上判断，而不是站在"机制证明它没问题"上判断。**

### 改了四处（同一原则：宁可炸，不给假绿灯）

| 场景 | 改前 | 改后 |
|---|---|---|
| 传错目录（非 git 仓库） | 跳过历史扫描，**仍报 CLEAN** | **ABORT** + 退出码 `2` |
| 文件清单被 `MAX_FILES` 截断 | 打印一行提示，**仍报 CLEAN** | **ABORT**（漏扫的结论不可信） |
| `--staged` 在非仓库目录跑 | `git diff` 静默返回空 → **报 CLEAN** | **ABORT** |
| `RESULT: CLEAN` 那一行 | 光秃秃一个结论 | **附带统计**：`scanned: 14 commits + 143 files [仓库路径]` |

**"干净"必须自带证据。** 没有 `scanned:` 那一行就不算跑过。

### 退出码约定（新增）

| 码 | 含义 | 动作 |
|---|---|---|
| `0` | 干净 | 可以继续 |
| `1` | 发现疑似密钥 | STOP，逐条过目 + 改历史 |
| **`2`** | **扫描没跑成** | **结果无意义，必须重跑** |

### 四场景实测

| 场景 | 期望 | 实测 |
|---|---|---|
| 裸跑（非 git 仓库） | ABORT rc=2 | ✅ `REPO 不是 git 仓库：F:\LottBuild` |
| 传仓库路径 | CLEAN rc=0 | ✅ `scanned: 14 commits + 143 files` |
| `--staged` 在仓库内 | 正常 rc=0 | ✅ `staged: 0 files`（工作区确实干净，真 0） |
| `--staged` 在非仓库 | ABORT rc=2 | ✅ |

### 连带修正

- `MEMORY.md` 与技能 `pre-push-secret-scrub/SKILL.md` 里的调用命令
  改为**显式传仓库路径**：`python F:/LottBuild/_secret_sentinel.py "<仓库绝对路径>"`
- 补上「三处副本必须同步、用 md5 比」的提醒
- 已确认**没有任何脚本自动调用哨兵**（签名变化无连带影响）

## 三、踩到的一个工具坑（也记进日志了）

改脚本 docstring 时写了两处 Windows 路径（`F:\LottBuild`），触发了
`SyntaxWarning: invalid escape sequence '\L'`。

修的过程中发现：**反斜杠在「工具 → bash heredoc → python」这条链路上会被吃掉一层**，
同一段文本经由不同工具写进去，反斜杠层数不一样。最后用 `chr(92)` 拼出反斜杠才绕开。

> 教训：**凡是跨工具的字符串，别用反斜杠字面量** —— 要么用正斜杠，要么用 `chr(92)` 构造。
> 这类失真和「工具输出本身就是泄漏通道」是同一族问题：**中间那一层也在改你的数据**。
