## 一、回答少爷的两个疑问

### Q1：「bat 提示对吗？」

**对。** 当时输出的 `Everything up-to-date` + `[SUCCESS] pushed to GitHub.`
意思是「本地和远端一模一样，没有新东西要传」。

原因是：那批审计修正**当时还没提交**（工作区有改动 ≠ 有提交）。
bat 本身没坏，只是没什么可推的。

### Q2：「为什么 Releases 页面没更新？README 徽章还是 v1.5.0？」

**根因：README 徽章读的是 GitHub 的 Release，不是仓库里的 README 文件。**

```
代码 push 成功  ≠  Release 存在
```

之前只 push 过代码，tag 只有 `v1.5.0`，**从来没建过 Release** →
徽章走 `GET /releases/latest` 拿不到任何 Release，就永远显示最旧的那条。

**每次发版必须三步齐全，缺一步就出这个症状：**

| 步骤 | 操作 | 作用 |
|---|---|---|
| ① 提交 | `git commit` | 代码进本地历史 |
| ② 推送 | `git push` | 代码进远端 |
| ③ **建 Release** | GitHub API + 传 APK | **徽章 / Releases 页面读这个** |

## 四、`推送到GitHub.bat` 已升级

改造成**两段式推送**，以后遇到历史分叉不用再找 AI：

1. 先试普通 `git push`（正常情况就够）
2. 被拒（`non-fast-forward` / `fetch first`）→ **提示少爷手动输入 YES** 确认
   → 走 `git push --force-with-lease`

用 `--force-with-lease` 而不是 `--force`：远端被别处改过时会**自动中止**，不会静默覆盖。

**已按编码规范验证**：
- 字节级：`非ASCII=0  CRLF=191  裸LF=0  首3=40 65 63`（纯 ASCII + 全 CRLF，无 BOM）✅
- cmd 实跑：模拟被拒场景 → 降级提示触发 → force-push 分支执行 → `[SUCCESS]` ✅

## 五、遗留事项（都不影响使用）

1. **远端仓库 `size` 仍显示 64 MB** ——
   force push 后旧提交变"孤儿"，GitHub 服务端**定期 gc 才会回收**（几小时~几天），

   想立刻瘦身只能删库重建 —— **不建议**，代价远超收益。

2. **旧版本 Release 附件仍在** —— v1.5.0 / v1.6.0 的 APK 还挂在各自 Release 上。
   Release 附件是独立存储、不进 git，**留着合理**（用户能下载历史版本）。

## 六、本次沉淀的三条通用经验

1. **「代码 push 了」≠「Release 存在」** —— 徽章读 Release。发版三步缺一不可。
2. **重写历史后必须 force push + 逐个重指悬空 tag** —— tag 会指向被剔除的旧提交。
3. **沙箱其实能推 GitHub** —— 只要少爷先跑过一次 bat（代理写进 repo 的 git config）。
   旧记录写的「沙箱推不上去是既定设计」已更正。
