| #   | 操作      | 预期                                       | 结果 |

| 1.3 | 点「录入彩票」 | 进拍照页；未配平台时弹提示「拍照识别需先配 AI 平台；也可直接用「手工填写」」 | ☐  |

> ⚠️ **1.3 的行为本期改过**。以前没配平台会直接跳设置页，  
> 但那样连「手工填写」也一起锁住了 —— 而手工录入恰恰是**唯一不依赖 AI** 的功能。  
> 现在一律放行到拍照页，由少爷自己选路：拍照识别（需配平台）或手工填写（不需要）。
>
> ⚠️ 「没配平台不让白拍」这条保护**仍然有效**：真按了拍照按钮，会提示去配平台，不会白跑识别。

## 20. 🎯 第二阶段（二）：开奖查询 + 自动对奖 + 定时核验

## 22. 💾 数据备份与恢复（少爷选的 B，2026-09-26）

> **这一批解决的是一条真实风险**：账目只存在手机里，卸载 App、换手机、手机丢了 = 全没了。  
> 前面做的对奖、盈亏、统计，全建立在那一份数据上。

### 怎么用

**设置 → 数据备份**

- **导出备份** → 弹系统文件选择器 → 选存哪  
  （建议存到网盘：微信收藏、夸克、OneDrive 都行，这样手机丢了也还在）
- **恢复备份** → 选那个 `.json` 文件 → **先弹预览**告诉你「会新增几张、跳过几张」→ 再确认

### 几个设计决定（都是刻意的）

| 决定                       | 为什么这么做                                                                              |
| ------------------------ | ----------------------------------------------------------------------------------- |
| 导出成 **JSON 文本**，不是拷数据库文件 | 数据库开着 WAL 模式，直接拷 `.db` 会**静默丢掉最后一批写入**——你看着备份成功，实际少几张票；而且跨版本恢复会撞上「版本不对就清空重建」，把数据全清了 |
| 恢复是**合并**，不是覆盖           | 不做「清空后恢复」——那等于给你一个「一键删光账目」的按钮，误点一次就没了                                               |
| 同一份备份**反复导入不会重复**        | 按票身份指纹去重；指纹缺失时按「彩种+期号+购买时间+金额」比对                                                    |
| **API Key 不进备份**         | §17 硬要求。Key 存在系统密钥库里，换手机本来也得重填                                                      |
| 不备份「AI 调用记录 / 识别草稿」      | 那是运行日志性质，丢了不影响账目                                                                    |
| 文件带缩进格式                  | 体积大 30%，换来**人可读**——万一哪天 App 起不来，能用文本编辑器把号码抄出来                                       |

## 23. ✍️ 手工录入 + 复式 / 倍投（少爷选的 C，2026-09-26）

> **这一批起因是发现两处硬伤**，它俩合起来正好把「复式录入」堵死了。

### 硬伤一：期号、开奖日期**根本改不了**

核对页原来用的是一个只读的字段行组件，而且**它的编辑回调从来没被调用过**  
（调用处传的是 `onChange { it.copy(issue = it.issue) }` —— 看着像在改，其实是空操作）。

后果：**AI 把期号或开奖日期读错，少爷没有任何办法修正，只能放弃重拍。**  
可这两项恰恰是**对奖的必需信息** —— 读错就等于错到底。

现在三项全可编辑，日期还支持「敲 8 位数字自动补横线」（`20260926` → `2026-09-26`），  
免得在手机上切键盘敲横线。

### 硬伤二：没有手工录入入口

以前所有票都必须经过拍照识别。AI 读不出来（拍糊了、平台欠费、没配 Key、断网）时，  
**唯一的办法是反复重拍**。而**复式票恰恰是最容易读错的一类** —— 十几个号码挤一行。

现在：拍照页底部有「不拍照，手工填写」。

### 复式 / 倍投怎么用

**复式**：选号面板**直接多点几个**就行 —— 比单式需要多（双色球红球 >6、大乐透前区 >5 或后区 >2）  
就自动判为复式，注数实时算给你看。

**倍投**：「投注参数」区用 −/+ 调倍数（1~99），大乐透还能勾「追加投注（每注 +1 元）」。

**多注**：每注一张卡，右上角可删除；底部「+ 添加一注」。删中间一注会自动重排编号，不会出现「第 1 注、第 3 注」。

### 一个刻意的取舍

**单式/复式只自动「升级」，不自动「降级」。**

- 选了 7 个红球 → 必然是复式 → 自动改（这是硬事实，不可能错）

这种判断只能交给人。

## 24. 🔍 票列表筛选与搜索（少爷选的 F，2026-09-26）

> 票会越攒越多。这一批解决「翻半天找不到那张票」。

### 入口

首页右上角**漏斗图标**（在「日志」「设置」左边）。点一下展开筛选面板，再点收起。  
筛选生效时：图标变主色 + 带一个角标数字（表示有几个条件在生效）。

### 两个「组合档」是按真实问法设计的

| 档位      | 包含哪些状态            | 为什么这么分                    |
| ------- | ----------------- | ------------------------- |
| **待开奖** | 未开奖 + 等待开奖结果      | 对少爷来说这俩是同一件事：还没对奖。分开筛会很别扭 |
| **已中奖** | 奖金待确认 + 待兑奖 + 已兑奖 | 想「我中过哪些奖」时，不会想分三次筛        |

**「已过期未兑奖」单独一档，不在「已中奖」里** ——  
它虽然中过奖，但钱没拿到。混在「已中奖」里会让中奖金额对不上。

### 一个重要决定：筛选**不影响**上面的统计

hero 卡的「净收支」始终是**全部票**的。理由：

如果净收支跟着筛选变，那「净收支」这四个字在不同筛选下代表不同东西 ——

## 25. 📥 批量导入（少爷选的 H，2026-09-26）

> 交接稿 §8 的最后一项，也是第三阶段最后一项。

### 怎么用

拍照页 →「**批量导入照片**」→ 一次选多张 → App 逐张识别 → 完成后分类告诉你结果。

### 逐张串行，不做并发

交接稿写「可限制并发，例如 2 张同时」，我选了**串行**：

| 理由     | 说明                        |
| ------ | ------------------------- |
| 并发收益有限 | 单张本来就要几秒~几十秒，省下的时间不多      |
| 风险明显更高 | 一旦触发平台 QPS 限流，**整批**都可能失败 |
| 进度才说得清 | 串行下「第 3/13 张」才有确定含义       |
| 好定位问题  | 出错时知道是哪张的事                |

真要做并发得先有「按平台限流 + 失败退避」，那是另一个量级的工作。  
这段循环改成并发只要几行，但**先把正确性做踏实**。

### 三类分诊（§8 的「批量完成页」）

| 分类         | 判据                     | 处理       |
| ---------- | ---------------------- | -------- |
| **可以直接入账** | 结构完整、**连警告都没有**、不是重复   | 一键入账     |
| **需要你确认**  | 有错 / 有警告 / 字段冲突 / 疑似重复 | 逐张核对     |
| **好像重复**   | 完全重复（同一张实体票已入账过）       | 自动跳过并删草稿 |

⚠️ **有警告也算「需要确认」**。比如「票面金额与推算对不上」是个真问题，  
自动入账等于把这个错误固化进账目。

### 草稿 = 队列（这是「不怕中途退出」的关键）

每张识别成功就存一条草稿，草稿表在这里当**队列**用：

```
识别成功 → 存草稿（入队）
核对入账 → 删草稿（出队）
放弃     → 删草稿（出队）
闪退/退出 → 草稿还在，首页提示可点进去接着核对
```

所以**中途退出不丢票、不白花 API 钱**。

顺带修了一个老 bug：以前入账后**草稿不删**，导致首页那条「有 N 张还没核对」  
永远不消失、越攒越多。

### 27.5 为什么可以确信「没动设置项」

将来如果有人给设置表加了清空方法、或者图省事改用 Room 的 `clearAllTables()`  
（那会一次清掉 8 张表），测试会立刻红。

### 29.1 「单式多注」不再被误报成复式

> 一次识别的量级参考：图片本身 ~1300 token + 提示词 ~300 token + 模型思维链 ~150 token ≈ **一次约 1800 token**。  
> 豆包这个模型带思维链（响应里有 `reasoning_content`），所以输出 token 比纯问答多，属正常。


### ⚡ 识别耗时——真机实测（这是本次最关键的发现）

少爷 2026-09-26 的真机日志（**两张票都识别成功并入账**）：

### 30.1 投注构成要说清楚（组合票不再是「复式」两个字）

## 34. 🐛 v1.5.2：闪退根因修复（2026-09-27 夜）

### 34.1 根因与修法

**第 33 版的崩溃屏抓到了确凿堆栈**（少爷录屏截图）：

```
java.lang.NullPointerException: Attempt to invoke interface method
'void kotlinx.coroutines.flow.MutableStateFlow.setValue(java.lang.Object)'
on a null object reference
    at com.bro.lotteryledger.ui.MainViewModel$loadThemeMode$1.invokeSuspend(MainViewModel.kt:317)
```

**翻译成人话**：

1. `MainViewModel` 里有个 `init` 块（对象创建时先跑），它调用 `loadThemeMode()`
2. `loadThemeMode()` 内部启动一个协程，里面写 `_themeMode.value = ...`
3. **但 `_themeMode` 这个字段的声明写在 `init` 块的下面**
4. Kotlin **按从上到下的顺序**初始化字段 —— `init` 跑的时候，`_themeMode` **还是 null**
5. 于是「在 null 上写值」→ 崩溃

**为什么平时不崩、偶尔才崩**：协程通常是排队执行的，等轮到它时 `init` 早跑完了，
字段也有值了。但 `viewModelScope` 用的调度器是 `Dispatchers.Main.immediate` ——
**如果调用时已经在主线程，协程体会立即执行**。这时 `init` 还没跑完，于是炸。

**这也是为什么 1.4.0 完全正常**：`loadThemeMode()` 和 `loadSkin()` 都是 **v1.5.0 新加的**
（主题自选 + 三套皮肤那一批）。

**修法**：把 `_themeMode` / `_skin` 两个字段的**声明位置提到 `init` 块之前**。
同时在该处和 `init` 块都留了醒目注释，防止以后再犯。
